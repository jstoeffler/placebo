# Dogfood suite

The suite in `.placebo/` asks one question: does Placebo's own `AGENTS.md` help an agent work on Placebo? Control is the repo as it is at the pinned commit; the `none` treatment applies `variants/none.patch`, generated by `placebo init`, which deletes `AGENTS.md`, `CLAUDE.md` and `.claude/` (the writing-rules skill and the hook that lints and typechecks every edit). Rules that show no effect are candidates for deletion (brief §3).

Each task is a small, unambiguous change in core's pure layers, written the way a maintainer writes an issue. A hidden Vitest file, injected after the agent finishes, decides pass or fail; a checklist asks the judge whether the change follows the conventions `AGENTS.md` states; a comparison pits the two arms against each other blind.

| Task | Asks for | Hidden test |
| --- | --- | --- |
| `compact-tokens` | a compact token count formatter (`12.3k`, `1M`) | `packages/core/src/statistics/hidden-compact-tokens.test.ts` |
| `single-comparison` | a suite rule: at most one comparison grader per task | `packages/core/src/domain/hidden-single-comparison.test.ts` |
| `trimmed-mean` | a trimmed mean with a stated formula | `packages/core/src/statistics/hidden-trimmed-mean.test.ts` |
| `task-id-from-title` | a task id derived from a commit subject | `packages/core/src/kernel/hidden-task-id-from-title.test.ts` |

With four tasks the result describes these tasks, not the repo in general; the report says so.

## Running it

From the repo root, after `pnpm install && pnpm build`:

```
pnpm --filter placebo-eval exec placebo run --runs 1   # a first pass, one run per task per arm
pnpm --filter placebo-eval exec placebo run            # the experiment, 5 runs per task per arm
```

`--task <id>` runs one task. The run uses your Claude Code login and costs real tokens: one run per arm of one task, judge included, cost about $0.50 at the pinned models. `placebo clean --snapshots` reclaims the disk afterwards. The **Dogfood** workflow runs the same thing on GitHub Actions on demand (`docs/ci.md`).

## Adding a task

1. Pick a change that is small, has one right answer, and lives in core's pure layers (kernel, domain, statistics, formatting).
2. Write the prompt as an issue: what and why, the exact rules the hidden test checks, and a "Must keep working" line naming the entry point the test calls. Say nothing about where the code lives.
3. Put the hidden test at `.placebo/tasks/<id>/<destination path>`, for example `.placebo/tasks/<id>/packages/core/src/statistics/hidden-<id>.test.ts`, and list the destination under the command grader's `hidden`. The test imports through core's public entry point (`../index.js`), so a solution that names its file differently still passes.
4. Grade with `{ type: command, run: "pnpm vitest run <destination> --project core", hidden: [<destination>] }`, `file_modified` only where every sensible solution touches that file, a `checklist` of three to five yes/no questions in `tasks/<id>/checklist.md`, and `{ type: comparison }`.
5. Validate the task (below), then keep the reference solution out of the repo so the task stays honest.

## Validating a task

Every task passes this check before it is committed, the same one task mining will apply:

```
git clone . /tmp/placebo-task-<id> && cd /tmp/placebo-task-<id>
git checkout <commit from suite.yaml>
pnpm install --frozen-lockfile
cp <repo>/.placebo/tasks/<id>/<destination> <destination>
pnpm vitest run <destination> --project core     # must fail: the function does not exist
# write a reference solution by hand
pnpm vitest run <destination> --project core     # must pass
pnpm vitest run --project core && pnpm typecheck # the rest of core stays green
```

Then delete the clone. A hidden test that passes before the change, or fails against a correct solution, is a broken task: fix the test or the prompt, never the reference.

When the suite's `commit` moves, validate every task again at the new commit.
